# First offline mining exercise

From the project root in PowerShell:

```powershell
.venv\Scripts\python.exe -m dojo mine-demo
.venv\Scripts\python.exe -m dojo mine --repo data/mining-demo --dry-run
```

The first command creates a new, ignored local Git repository containing two
synthetic commits. It uses a fictional author, disables hooks/signing, makes no
network requests, and never adds a remote. It refuses to reuse an existing path.
On later visits, run only the second command.

The base version's `add` function subtracts; the fix changes it to addition and
adds `assert add(2, 3) == 5`. The reader compares the fix to its parent without
checking anything out or executing the inspected code or tests. Added plus
deleted lines total six (two source lines and four test lines).

Expect `parent_count: 1`, one source file, one test file,
`eligibility: candidate`, `rejection_reasons: []`, and `validation: not_run`.
This fixture is learning material, never evidence of real benchmark yield.

This command inspects one commit, not an entire history. Test-file naming is
currently a Python convention (`tests/`, `test_*.py`, or `*_test.py`), not a
universal classifier. Renames appear as deletion/addition. Root commits have no
base and therefore no file comparison; merges are identified by parent count.
The candidate filter rejects commits without exactly one parent, missing Python
source/tests, more than five source files, more than 150 added/deleted lines,
binary changes, known generated paths, lockfile-only changes, invalid dates,
future dates, and dates older than the configured window. Both date endpoints
are inclusive. The default window is nine calendar months; narrow it with
`--window-months 6` (allowed range: 6–9). The cutoff clamps month-end dates and
uses UTC and the Git committer timestamp. Git timestamps can be rewritten, so
commit age is a heuristic, not proof of freedom from training-data contamination.

Generated paths are detected using directory names such as `generated`,
`_generated`, `autogenerated`, `build`, `dist`, `__pycache__`, `node_modules`,
`.venv`, `.tox`, and common protobuf/minified/bytecode suffixes. These heuristics
can miss generated files or flag hand-written files in those directories; review
the repository's conventions before using real candidates. Mixed lockfile/code
changes are permitted if the other criteria pass. The report includes the
effective filter policy and all rejection reasons. Rejection is a normal report,
not a CLI error; invalid options/repositories produce an error exit.

The owner wrote the first three checks and requested implementation of the
remaining filters. Boundary tests now cover them and the CLI reports decisions.
The following section covers the first synthetic Docker validation slice.

## Validate the synthetic task

The first Docker validation slice now supports only the exact synthetic addition
fixture. It refuses other committed content, additional files and symlinks.
It reads committed snapshots, leaving the existing checkout unchanged. The test
diff and reference-source diff are separate; base receives only the new tests.
The reference fix is never added to the baseline code.

With Docker Desktop running and the image already built:

```powershell
.venv\Scripts\python.exe -m dojo mine-validate-demo
```

For a fresh installation, build the environment first (this setup downloads
Python/pytest; the subsequent test runs have no network):

```powershell
docker build --file docker/Dockerfile.validation-demo --tag dojo-validation-demo:local docker
```

Only the docker directory is used as build context. The base image digest and
pytest version are pinned; the result records the actual local image ID.
Runtime containers use an explicit local Docker endpoint, no host mounts or
forwarded credentials, no network, a non-root user, a read-only root filesystem,
dropped capabilities, no-new-privileges, and CPU/memory/process limits. Fresh
snapshots arrive over stdin and only /tmp is writable. Containers are removed
by their unique names, including after a timeout. No host execution fallback
exists. Docker isolation reduces exposure; it is not an absolute safety promise.

Expected result: `validated_synthetic_demo`, with four run receipts. Twice, the
regression `test_positive_numbers` fails before the fix and passes afterward;
`test_zero` passes in every run. Collection/setup/teardown errors, skips, changed
image IDs, inconsistent repeats and unexpected test outcomes reject the result.
There is a shared 60-second acceptance deadline and per-run timeout.

This does not validate arbitrary repositories or count toward the 40-task yield
gate. Generic snapshot/patch handling, dependency environments, full-history
enumeration and real-task export are still pending. No model is involved yet.
